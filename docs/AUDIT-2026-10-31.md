What this repo does: This is a private, single-user habit tracker with daily habits, timed activities, dated notes, and SQLite backup and restore. The server database is authoritative. This audit assumes one NAS container running one Uvicorn process, with overlapping requests from the user's browsers and the backup and timer jobs.

Audited upstream `master` at `c08090daa410defc2cfd7e2eb1105013ca43afa4` on 2026-10-31. This PR adds only this report; it does not fix the findings or include the original checkout's uncommitted frontend work. Source line numbers below refer to that audited commit.

**Must fix**

1. **P1 — Web requests can read files outside the web directory** (`backend/app/main.py:517-522`)
   - **What this is:** The fallback route serves frontend files and direct page URLs.
   - **Problem:** It joins the request path to `frontend/dist` without checking that the result stays inside that directory. A request for `/%2e%2e/%2e%2e/backend/pyproject.toml` returned that backend file with HTTP 200 in the actual app; further traversal can reach other files readable by the server account.
   - **Fix:** Resolve the requested path and require it to remain inside the resolved frontend directory before serving it. Add a regression test using an encoded parent-directory path.
   - **If we skip it:** Anyone who can reach the private app can also fetch server-readable files outside the intended static files, including sensitive files mounted in the container.

2. **P1 — Restore and import can lose successful concurrent writes** (`backend/app/database.py:62-75,2208-2213,2311-2321`)
   - **What this is:** Replacement creates a safety snapshot, swaps the database file, and removes SQLite's temporary write files.
   - **Problem:** Replacement takes `_replacement_lock`, but ordinary database connections never take that lock. In a controlled interleaving, a habit creation succeeded after the safety snapshot and before replacement, then disappeared from both the restored database and the safety snapshot.
   - **Fix:** Make every live database connection share the replacement lock for its entire lifetime, including reads and background jobs, in the supported single-process deployment. Test that a write arriving during replacement waits and then reaches the replacement database.
   - **If we skip it:** A second browser can receive a successful save while its data is lost during restore or import, with no safety copy containing it.

3. **P1 — An invalid date in an import can replace working data and break Today** (`backend/app/database.py:2009-2026,2314-2319`)
   - **What this is:** Import checks database integrity and required table columns before replacing live data.
   - **Problem:** It does not validate stored date values. A database built from the repository's legacy schema with a habit starting on `0000-01-01` passed import and replaced live data; the next `habits_on(today)` raised `ValueError` while parsing that date.
   - **Fix:** Validate stored dates and the row values required by readers on the staged copy before replacement, and reject invalid data with `ImportValidationError`. Add a malformed-date import test that also verifies the live database stays unchanged.
   - **If we skip it:** A structurally valid but unusable upload can take the main screen down until the user restores the safety backup.

4. **P2 — A failed scheduled backup is recorded as completed** (`backend/app/database.py:2285-2301`)
   - **What this is:** The scheduler tracks the last daily or weekly backup date so a due backup runs once.
   - **Problem:** It commits the due date before creating the backup. After injecting a temporary storage error and restoring storage one minute later, the next run skipped that due backup because its date was already marked complete.
   - **Fix:** Record successful completion only after backup creation succeeds, coordinating the operation with the existing lock. Add a failure-then-recovery test showing that the same due backup is retried.
   - **If we skip it:** A brief storage failure leaves a daily or weekly backup missing until the next scheduled period, even after the server recovers.

5. **P2 — Concurrent duration writes can exceed the daily limit** (`backend/app/database.py:1233-1248,1255-1276`)
   - **What this is:** Manual duration entry checks that the day's total stays at or below 1,440 minutes.
   - **Problem:** The total is read before the write transaction starts, so overlapping requests can both approve the same remaining capacity. With 1,400 minutes already saved, two coordinated 30-minute additions both succeeded and left 1,460 minutes in the database.
   - **Fix:** Start `BEGIN IMMEDIATE` before the reads in both add and update, following the timer methods' existing pattern. Add a two-connection test proving that only one addition succeeds when the combined result would exceed the limit.
   - **If we skip it:** Ordinary use from two tabs or devices can save totals the product explicitly forbids and interfere with later timer capacity checks.

6. **P2 — Built-in charts show zero for activities created during the period** (`frontend/src/components/TimedStatistics.tsx:14-20,31-38`)
   - **What this is:** Week, Month, 6 months, and Year choose their normal calendar boundaries.
   - **Problem:** The load effect rejects any range starting before the activity's start date, including these built-in ranges. In Chromium, an activity starting Wednesday 2026-10-28 with 90 saved minutes showed `1h 30m` for the day but `0m` for the week, and made no statistics request.
   - **Fix:** Clamp built-in range starts to the activity's start date while retaining validation for custom input. Test an activity created midweek and midmonth.
   - **If we skip it:** New activities show false zero totals until the selected period no longer starts before the activity, or the user chooses All time.

7. **P2 — Charts stay stale after duration edits** (`frontend/src/components/TimedStatistics.tsx:33-38`; `frontend/src/App.tsx:334,356`)
   - **What this is:** Entry mutations refresh the selected day's entries and total while the statistics component stays mounted.
   - **Problem:** The chart's load effect has no dependency that changes after an entry mutation. In Chromium, adding 10 minutes to a 90-minute activity changed the day total to `1h 40m`, but All time remained `1h 30m` and no new statistics request ran.
   - **Fix:** Pass an explicit refresh counter to the chart and increment it after successful entry changes and timer completion, using the app's existing refresh pattern. Test add, edit, and delete without closing the detail view.
   - **If we skip it:** The same screen shows conflicting totals and outdated bars until the user changes periods or reopens it.

8. **P2 — An archived activity can start a hidden live timer** (`backend/app/database.py:527-536,922-970`; `frontend/src/App.tsx:235-236`)
   - **What this is:** Historical date checks keep the archive date active so that day's history remains available.
   - **Problem:** Timer creation reuses that historical check without rejecting a currently archived activity. Creating an activity, archiving it today, and starting a one-minute countdown all succeeded; a stale second browser can therefore start a timer for an activity that Today filters out.
   - **Fix:** Reject a non-null current `archived_at` when starting a live timer, while retaining the inclusive archive-day rule for history. Add a start-after-archive test.
   - **If we skip it:** A timer can run and record duration while its activity is hidden from the active Today list.
